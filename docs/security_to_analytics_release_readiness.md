## 3. 세션 정리 방법과 승인 범위

공식 SDK는 서버에서 `auth.admin.signOut(targetUserJwt, 'global')`이다. 첫 인수는 대상 Auth ID/서비스 키가 아니라 대상 사용자의 유효 로그인 JWT다. 현재 확보된 로컬 캐시 access token은 exp가 지났고, 두 대상 모두에 대한 실행 수단은 확보되지 않았다. 공식 사용자 상세 UI 점검에서도 직접 전체 세션 폐기 버튼은 확인하지 못했다. 미확인 ID 기반 메서드나 Auth 내부 테이블 DELETE를 실행하지 않는다.

후속 승인은 비공개 명부의 정확한 두 Auth ID에 연결된 세션/refresh 자격만 대상으로 하며 실제 관리자 3개/다른 회원 세션과 계정·댓글·감사 기록은 제외한다. 유효 JWT를 안전하게 사용할 수 있는 경로나 Supabase가 확인한 ID 기반 관리 방법을 확보한 뒤 구체적인 방법과 영향을 제시하고 승인받아야 한다. 현재 승인만 요청해 곧바로 실행할 수 있는 준비 상태가 아니다. 새 로그인/refresh/magic link 발급도 별도 범위 판단 없이 하지 않는다.

전역 로그아웃은 refresh 자격을 폐기하지만 이미 발급된 access JWT의 exp를 소급 변경하지 않는다. 만료 전 민감 요청은 현재 DB 역할/세션 검증이 중요하다. ban은 새 로그인 제한이며 세션 폐기의 대체물이 아니다. ban·삭제·역할 변경은 이번에 수행하지 않았다. [관리자 signOut](https://supabase.com/docs/reference/javascript/auth-admin-signout), [로그아웃 범위](https://supabase.com/docs/guides/auth/signout), [사용자 관리](https://supabase.com/docs/guides/auth/managing-user-data).

[개인정보보호위원회 2026.4 작성지침](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS217&mCode=G010030000&nttId=12018) 공식 게시 상태를 재확인했다. 승인 목록 해소 전 GA 활성화/정책 게시 준비 완료로 보지 않는다.

## 8. 추가 개발 없이 처리 가능한 작업

운영자가 본인 계정으로 OAuth/이메일 로그인·프로필 저장·권한별 화면을 확인하고 결과를 제공할 수 있다. 실제 회원 데이터를 임의 시험하지 않는다. 사용할 GA 스트림 ID와 계약/보존/처리방침 승인 정보를 확정하고 별도 테스트 속성을 준비할 수 있다. 테스트를 중단하고 지정 E2E 자격/캐시를 분리·폐기할 수 있으나 이번에는 변경하지 않았다. 세션 폐기는 수단 확보와 별도 승인이 필요하다. 이전 보안 SQL을 다시 실행할 필요는 없다.

## 9. 다음 운영 배포에 포함할 변경

가입 통계 4런타임 파일만 우선 후보로 한다.

- apps/web/app/api/admin/signup-stats/route.ts
- apps/web/lib/authSignupStats.ts
- apps/web/app/components/AdminSignupStats.tsx
- apps/web/app/admin/page.tsx

관련 기존 테스트/문서는 함께 검토하되, GA4·UTM·개인정보 정책 게시·OAuth role 전송 복원·새 migration은 포함하지 않는다. 현재 검증 작업 트리는 detached 임시 조합이며 다음 운영 SHA는 아직 확정/배포하지 않았다. 통계 후보는 현재 보안 릴리스 위에 분리 커밋하고 새 Preview 검증·별도 승인 후 배포해야 한다.

## 10. 후속 실행 순서와 검증 증빙

1. 핵심 관리자 취약점/권한 회수는 완료로 기록하고 세션·E2E 분리·실계정 smoke를 잔여 항목으로 유지한다. 운영 E2E가 강등 계정을 다시 관리자로 만들지 않도록 운영 자격 재사용을 중단한다.
2. 운영자가 승인된 본인 계정으로 정상 로그인·최소 정상 저장을 확인한다. 세션 폐기는 두 대상만의 방법/영향을 제시한 뒤 별도 승인받는다. 서비스 관리 키 전체나 실제 관리자 세션을 일괄 폐기하지 않는다.
3. 현재 보안 코드에 가입 통계만 분리한 릴리스를 준비하고 새 Preview에서 최고 관리자 집계·일반 admin/user 거부·응답 개인정보 제외를 재확인한다. 지표 의미/부하 한계 수용 후 운영 배포를 별도 승인받는다.
4. GA 측정 ID 불일치 및 개인정보 승인 사항을 해소한다. 보안 role 미전송을 보존한 GA 분리 통합을 검토한다.
5. 별도 테스트 GA 속성·분리 DB/Preview로 실제 DebugView 수신을 검증한다. 이때도 운영 수집은 비활성이다.
6. 정책 게시와 운영 GA 활성화 각각의 최종 승인을 받은 뒤에만 진행한다. 현재 작업에서 실행하지 않는다.
