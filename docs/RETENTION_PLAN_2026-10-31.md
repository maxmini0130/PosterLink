# PosterLink 재방문·가입 전환 개선 지시서 (2026-10-31)

> 대상: Claude Code
> 스택: Next.js (App Router) + Supabase + Vercel, Expo WebView 앱
> 범위: 0단계 측정 → 1단계 지역·콘텐츠 → 2단계 비회원 저장과 가입 연결 → 3단계 회원 홈
> 4단계(공유 노출 개선, 홈 화면 추가 안내, 앱 푸시, 카카오)는 이번 범위가 아니며, 마지막에 메모만 남깁니다.

---

## 목표와 핵심 성과

**이용 흐름**: 관심 공고 발견 → 가입 없이 저장·탐색 → 계정에 보관하며 가입 → 다시 와서 새 공고와 내 진행 상황 확인

**핵심 성과 지표**: 가입 후 **첫 찜·기관 구독·관심 조건 저장 중 하나 이상을 완료한 사람(이하 "활성 가입자")**의 수, 그리고 그 사람들의 7일·30일 재방문율.
가입 수만으로 성과를 판단하지 않습니다.

## 공통 원칙

1. **먼저 확인하고 고칩니다.** 각 단계는 기존 코드·스키마·이벤트를 먼저 조사해 보고하고, 그 위에 보완합니다. 이미 있는 기능(찜, 기관 팔로우, 알림 화면, `check-deadlines`, `notify-new-match`, 공유 버튼 등)은 새로 만들지 말고 재사용·확장합니다.
2. **운영 DB 쓰기, 마이그레이션 적용, 배포, push는 하지 않습니다.** 승인 후 진행합니다. Preview 환경이 운영 Supabase에 연결되어 있으므로 Preview에서도 쓰기 동작을 테스트하지 않습니다. 스테이징이 준비되면 그곳에서 검증합니다.
3. 아래 테이블·컬럼명은 **예시**입니다. 실제 스키마에 맞추고, 다르게 설계했다면 이유를 보고합니다.
4. 단계별로 브랜치·커밋을 분리하고, 각 단계 PR에 원인 근거·변경 전후·추가 테스트·전체 회귀 결과를 남깁니다.

## 1단계. 지역 정리와 콘텐츠 연결

개인화는 지역 정리(B) 반영 **이후**에 켭니다.

### 1-1. 지역 정리(B) 마무리

- 기존 브랜치 `fix/public-b-regions-20261025`의 작업(고정 기관 매핑, 시도 경계 규칙, 근거 미확인 처리 등)을 이어서 진행합니다. 운영 반영은 스테이징 검증 후 승인을 받습니다.

  - **공고 대상 지역**: 실제 참여·신청 대상이 되는 지역 (여러 개 가능)
- 개인화·지역 페이지·관련 공고는 **공고 대상 지역**을 우선 사용합니다. 마포구 소재 기관의 공고라도 전국 대상일 수 있습니다.

### 1-2. 지역 섹션 구분

관심 지역을 기준으로 공고를 세 묶음으로 나눠 보여줍니다. 섞지 않습니다.

| 섹션 | 기준 | 표시 |
|---|---|---|
| 내 지역 | 대상 지역에 관심 자치구 포함 | 기본 |
| 주변 지역 공고 | 대상 지역이 인접 자치구 | "주변 지역 공고" 라벨을 붙여 구분 |
| 서울 전체 / 전국 대상 | 대상 지역이 시 전체 또는 전국 | 별도 섹션 |

- 인접 자치구는 행정경계 기준 매핑 테이블로 관리합니다(하천을 사이에 둔 경우 포함 여부는 설정값으로).
- 내 지역 공고가 적을 때(예: 5건 미만) 주변 지역·유사 분야로 넓히되, 라벨로 구분합니다.

### 1-3. 공고 상세의 관련 공고 카드

현재 상세 하단의 "같은 신청 지역 공고 / 같은 분야 공고" 링크를 실제 공고 카드로 바꿉니다.

- 같은 기관의 접수 중 공고
- 같은 대상 지역 + 같은 분야의 접수 중 공고
- **종료된 공고**라면 상단에 "지금 신청할 수 있는 비슷한 공고"를 먼저 표시
- 카드 클릭은 `poster_view`의 출처를 `related`로 기록
- 지역 신뢰도가 낮은 공고는 "같은 지역" 추천에서 제외

### 1-4. 마포 공고 확보 (데이터 운영)

- 개발 범위는 아니지만, 마포 기관 목록(`마포구_기관목록.xlsx`)의 기관별 수집 상태를 관리할 수 있도록 운영 콘솔의 출처 관리에 "수집 방식(크롤링/현장 촬영/기관 등록/미수집)" 필드를 추가할지 검토 의견만 주세요.

## 2단계. 비회원 저장과 가입 연결

### 2-1. 비회원 저장

- 비회원도 **찜**과 **관심 조건(지역·분야)**을 저장할 수 있게 합니다. 브라우저 저장소에 스키마 버전을 붙여 저장합니다.
- 저장 위치를 명확히 안내합니다. 예: "이 기기의 브라우저에 저장됩니다. 기록을 지우면 사라질 수 있어요."
- 웹 브라우저와 앱 WebView의 비회원 저장은 각각 유지합니다.

### 2-2. 가입 안내

- 저장 직후, 또는 찜 목록에서 **"찜한 공고를 계정에 보관하기"** 안내를 보여줍니다. 강제하지 않습니다.
- 찜 개수에 따른 안내(예: 2~3개째)는 **실험 가능한 설정값**으로 두고 고정 기준으로 막지 않습니다.
- 계정이 필요한 기능에서는 가입으로 연결합니다: **다른 기기에서 보기, 기관 구독, 관심 조건 계정 저장, 알림 설정**.
- 문구 원칙: 가입 이유를 "기록을 보관하고 이어서 이용할 수 있다"는 이점으로 설명합니다. **"3초 가입"처럼 확인되지 않은 표현은 쓰지 않습니다.**

### 2-3. 가입 후 하던 행동 자동 완료

- 가입·로그인을 시작할 때 **돌아올 위치(`return_to`)와 하려던 행동(`pending_action`: 찜/구독/조건 저장 + 대상 id)**을 저장합니다.
- 로그인 완료 후 원래 화면으로 돌아와 그 행동을 **중복 없이** 완료하고, 완료 사실을 화면에 표시합니다.
- 카카오·네이버(iOS 앱은 Apple 포함) 로그인 리다이렉트를 거쳐도 유실되지 않아야 합니다(웹·WebView 모두). 로그인 수단은 UI 지시서 3-3 참고.

### 2-4. 비회원 기록 합치기

- 가입·로그인 시 비회원 찜·관심 조건을 계정 기록과 **합칩니다**. 같은 공고는 한 건만 남깁니다.
- DB에 `(user_id, poster_id)` 고유 조건을 두고 upsert로 처리합니다. 재시도나 웹·앱 동시 합치기에도 중복이 생기지 않아야 합니다.
- **서버 저장 성공을 확인한 뒤에만** 로컬 기록을 비우거나 "이전 완료"로 표시합니다. 실패하면 로컬 기록을 유지하고 재시도합니다(다음 진입 시 자동 재시도 포함).
- 각 환경(웹, 앱 WebView)에서 같은 계정으로 로그인하면 **그 환경의 기록**을 계정에 합칩니다.
- `pending_action`과 합치기가 같은 공고를 가리켜도 한 건만 남아야 합니다.
- 결과를 `guest_merge` 이벤트로 기록합니다.

### 2단계 수락 기준

- [ ] 비회원 찜·관심 조건 저장과 저장 위치 안내

## 3단계. 회원용 관심 홈

### 3-1. 상태 모델: 이용자 상태와 공고 상태를 분리

한 공고가 "신청했어요"이면서 "접수 종료"일 수 있습니다. 공고가 종료됐다고 이용자 기록을 덮어쓰지 않습니다.

| 구분 | 저장 위치 | 값 |
|---|---|---|
| 이용자의 관리 상태 | 찜 기록(예: `favorites.user_status`) | 관심 · 신청했어요 |
| 공고의 접수 상태 | 공고 계산값(공용 함수) | 접수 예정 · 접수 중 · 상시 모집 · 소진 시 마감 · 종료 · 마감일 확인 필요 |

- 공고 접수 상태는 이전 지시서(C)의 공용 상태 함수 하나로 계산합니다.
- **마감일 확인 필요**(마감일 신뢰도 낮음)와 **소진 시 마감** 공고는 D-day 표시와 날짜 기반 섹션("7일 안에 마감")에서 제외합니다.
- 선정·미선정 같은 결과는 이번 범위에서 다루지 않습니다. 나중에 추가할 때는 **이용자 직접 기록인지, 기관 공식 결과인지** 출처를 구분합니다.

### 3-2. "지난 방문" 기준

새로고침할 때마다 기준이 바뀌면 안 됩니다.

- 마지막 활동 후 **30분 이상** 지나 다시 들어오면 새 방문으로 봅니다.
- 새 방문이 시작될 때 **직전 방문 시각을 고정**하고, 그 방문 동안에는 바꾸지 않습니다.
- 직전 방문이 너무 오래전이면 기준을 **최근 30일**로 제한합니다.
- 첫 방문(직전 방문 없음)은 관심 조건에 맞는 접수 중 공고로 대신합니다.
- 회원은 서버에 저장하고, 비회원은 브라우저 저장소에 같은 규칙으로 저장합니다.

### 3-3. 회원 홈 구성

로그인한 회원의 첫 화면에 아래 순서로 보여줍니다. 섹션에 내용이 없으면 숨기고, 전체가 비면 관심 지역의 접수 중 공고로 대신합니다.

1. **지난 방문 이후 새 관심 공고** (관심 조건 기준, 1단계 섹션 구분 적용)
2. **7일 안에 마감** (오늘 포함 7일, 찜 공고 우선, 날짜 신뢰 공고만)
3. **접수를 시작한 찜 공고** (접수 예정 → 접수 중으로 바뀐 것)
4. **구독 기관의 새 공고**
5. **내 찜 공고**: 공고 접수 상태별로 묶고, 이용자 상태(관심/신청했어요)를 함께 표시

- 찜 카드에서 "신청했어요"를 직접 표시·해제할 수 있게 합니다(`apply_status_set` 기록).

### 3단계 수락 기준

- [ ] 이용자 상태와 공고 상태가 별도 저장·계산되고, 종료 공고의 "신청했어요"가 유지됨
- [ ] 상시 모집·소진 시 마감·마감일 확인 필요 공고가 날짜 기반 섹션에서 제외
- [ ] "지난 방문" 기준: 같은 방문 중 새로고침해도 목록 동일 / 30분 이후 재진입 시 기준 갱신 (fake timer 유닛 테스트)
- [ ] 빈 섹션 숨김과 전체 빈 화면 대체
- [ ] E2E: 회원 홈 섹션 렌더, "신청했어요" 표시 후 공고 종료 상태에서도 유지
