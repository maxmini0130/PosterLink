# 운영 테스트 관리자 계정 정리 조사와 계획

후속 확정: 운영자가 실제 관리자 3개의 유지와 테스트 관리자 2개의 제외를 확정했다. 백업/PITR 재확인, 보안 패치와 계정 정리의 통합 실행 순서 및 안전 복구는 [최종 실행 절차](admin_security_execution_runbook.md)를 따른다. 현재 문서의 계정 조사 사실은 조사 시점 기준이며 실행 직전 다시 대조한다.

2026-10-23. **조사·계획만 수행했다. 운영 계정·권한·데이터·테스트 환경변수·세션 파일을 변경하지 않았다.** 대상은 운영자가 지정한 두 테스트 계정뿐이며 실제 운영 관리자 3개는 변경 대상이 아니다. 이메일·Auth UUID·로그인 시각·계정별 건수는 Git에 넣지 않고 현재 Windows 사용자 전용 로컬 보고서에 보존했다.

## 조사 결론

두 계정은 Auth에 존재하며 현재 profiles.role=super_admin이다. 최근 성공 로그인은 Auth의 last_sign_in_at으로 확인해 비공개 보고서에 KST로 표시했다. 현재 계정으로 로그인하거나 비밀번호를 검증하지 않았으므로 이 조사로 로그인 이력이 새로 생성되지는 않는다.

**즉시 삭제보다 테스트 의존 분리 후 역할 회수·로그인 차단·세션 정리와 계정 보존을 우선 권고한다.** 연결된 댓글·관리자 감사 이력 등이 있으며, 실제 운영 FK의 NO ACTION 참조 때문에 Auth 삭제가 막힐 수 있다. 데이터가 테스트 계정에 연결됐다는 이유만으로 해당 데이터도 삭제 가능한 테스트 자료라고 판정하지 않는다.

최근 로그인 필드는 가장 최근 성공 한 건이다. 누가 로그인했는지, 사람/자동화 여부, 전체 로그인 이력·실패 시도는 구분하지 못한다. 별도로 auth.audit_log_entries에서 두 대상에 연결되는 최근 30일 action 집계를 조회했으나 해당 actor_id 조건에 일치하는 결과가 없었다. 수집/보존 설정을 확인하지 않았으므로 최근 사용이 없었다는 증거가 아니다. 잔존 Auth 세션도 확인했지만 저장된 세션 수만으로 현재 사용 중이거나 모두 유효하다고 판단하지 않는다.

## 실제 운영 참조 관계와 데이터

운영 웹 공개 자산의 Supabase 주소와 로컬 읽기 설정이 일치함을 확인했고, 로그인된 관리 대시보드 프로젝트도 같은 ref임을 확인했다. 프로젝트 표시 이름에 dev가 있어도 실제 운영에서 쓰는 프로젝트이므로 테스트 DB로 취급하지 않았다.

운영 pg_constraint를 SELECT로 조회해 다음을 확인했다. 로컬 migration 추측 대신 실제 FK 정의를 기준으로 정리했다.

| 참조                                                                           | 삭제 동작 및 영향                                                                              |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| profiles.id → auth.users.id                                                    | CASCADE: Auth 삭제 시 프로필 삭제 시도                                                         |
| admin_actions.actor_user_id → profiles.id                                      | NO ACTION: 연결된 감사 이력이 있으면 프로필/Auth 삭제가 막힐 수 있음. 실제 대상 연결 존재 확인 |
| comment_reports.handled_by → profiles.id                                       | NO ACTION: 연결 행이 있으면 차단 가능. 삭제 전 재확인                                          |
| comments.user_id → auth.users.id                                               | CASCADE: 댓글 삭제 및 후속 참조 영향                                                           |
| comments.parent_id → comments.id                                               | NO ACTION: 다른 댓글이 부모를 참조하면 삭제를 막을 수 있음                                     |
| comments.parent_comment_id, comment_reports.comment_id → comments.id           | CASCADE: 답글/신고 등 후속 삭제 가능                                                           |
| favorites, poster_favorites, 관심 카테고리, 기관 팔로우, 알림 구독, point_logs | 대상 Auth/프로필 삭제에 따라 CASCADE되는 실제 FK 존재                                          |
| notifications.user_id/recipient_id → auth.users.id                             | CASCADE, notification_delivery_logs도 알림 삭제에 따라 CASCADE                                 |
| notifications.actor_id → auth.users.id                                         | SET NULL                                                                                       |
| posters.created_by/approved_by → profiles.id                                   | SET NULL: 공고는 남아도 작성/승인 주체 참조를 잃음                                             |
| 방문·조회·신청 링크 로그의 user_id → profiles.id                               | SET NULL: 이력 주체 연결 상실                                                                  |
| poster_requests, poster_notice_candidates의 검토/요청 관련 FK                  | SET NULL                                                                                       |
| field_reports의 reporter_id/resolved_by → auth.users.id                        | SET NULL                                                                                       |
| Auth identities/sessions/MFA/OAuth 등                                          | 내부 CASCADE/SET NULL 관계 존재. 관리 API로 처리해야 하며 수동 SQL 삭제를 권고하지 않음        |

Data API GET/HEAD로 노출된 27개 참조/논리 참조 칼럼의 대상 건수를 확인했다. 검사 실패를 0건으로 처리하지 않았으며 이번 점검은 모두 건수 확인에 성공했다. 연결 종류에는 프로필·관심 카테고리·방문 이력·관리자 감사 이력·알림·댓글이 있다. 공고 작성/승인 소유 관계는 발견하지 못했고, 공개 공고 작성/승인 연결 건수도 0이었다. 계정별 숫자는 비공개 보고서를 참조한다.

Storage 객체는 owner와 owner_id 양쪽을 실제 DB에서 조회했으며 현재 두 대상의 소유 객체는 발견되지 않았다. Storage가 비어 있다는 사실만으로 다른 FK 문제를 해결하거나 삭제를 승인하지 않는다. JSON의 임의 UUID, 이메일 텍스트, 외부 연동·비노출 스키마 전체를 완전히 검증한 것은 아니다. 삭제 실행 전 참조를 재집계해야 한다.

추가 SELECT에서 대상 댓글의 공개 공고 연결·답글·신고 의존 건수는 현재 확인되지 않았다. 이는 댓글 본문이 삭제 가능한 테스트 자료라는 판정이나 이후에도 의존 행이 생기지 않는다는 보장이 아니다.

프로필/계정 생성 관련 실제 트리거 조회에서는 profiles의 updated_at 갱신 트리거만 확인됐고 auth.users에는 사용자 정의 트리거가 없었다. 자동 super_admin 부여 트리거를 발견하지 못했다. 전체 함수/외부 자동화가 없다는 보장은 아니다.

## 승인 후 권장 정리 순서

1. **테스트 의존 분리:** 새 테스트 프로젝트/환경 자격을 준비한 뒤 지정된 테스트 관리자 자격과 관리자 세션 파일만 교체·폐기한다. 실제 운영 관리자/일반 회원·운영자 세션은 건드리지 않는다. 외부/수동 E2E·모바일 작업 담당자도 확인한다. 현재 운영 Crawler 전체를 근거 없이 중지하지 않는다.
2. **보안 패치와 순서 조율:** 일반 회원이 role을 다시 올릴 수 있는 기존 취약점이 남아 있으면 단순 user 강등만으로 지속적인 회수가 보장되지 않는다. [확정된 웹/DB 보호 순서](profile_role_final_application.md)를 승인된 작업 창에서 먼저 완료하거나 회수와 연계한다. 침해 의심 시에는 별도 긴급 승인으로 로그인·세션·접근 제한을 우선 검토하고 패치까지 안전하다고 간주하지 않는다.
3. **역할 회수:** 담당자가 이메일과 정확한 Auth UUID를 보호된 화면에서 다시 대조하고 실제 최고 관리자 계정이 남는지 확인한다. 승인된 두 프로필만 super_admin에서 user로 변경하는 최소 작업을 계획한다. admin으로 내리는 것은 관리자 권한 제외 목표를 달성하지 못한다. 실제 운영 3개 계정은 명시적 제외 대상으로 재확인한다.
4. **로그인 차단·세션 폐기:** 담당자가 승인한 기간의 Auth ban과 해당 계정의 모든 세션/refresh 자격 폐기를 별도로 수행한다. 지원되는 관리 기능/버전에 맞는 구체적 절차를 실행 전에 확정한다. 새 로그인으로 토큰을 얻지 않는다. ban만으로 기존 세션 정리가 끝났다고 보지 않는다. 브라우저/모바일/CI의 저장 세션도 대상 계정만 폐기한다.
5. **검증·보존:** 기존 토큰의 관리자 API가 401/403으로 거부되는지, DB에 admin/super_admin 역할이 남지 않았는지, 실제 관리자 3개와 정상 서비스가 유지되는지 승인된 범위에서 확인한다. 댓글·감사 이력·FK 연결은 보존한다. 승인되지 않은 로그인·테스트 쓰기를 수행하지 않는다.
6. **삭제는 별도 후속 승인:** 데이터 담당자가 관련 댓글·감사 기록의 보존/보관·익명화 필요를 검토한 뒤에만 고려한다. NO ACTION을 우회하려고 감사 이력 삭제·actor_user_id 일괄 NULL·FK 제거·CASCADE 추가를 하지 않는다. 필요하면 별도 스키마/보존 설계를 승인받는다. 삭제는 최종 Auth 관리자 API로 정확한 대상에 한정하고, SQL 직접 삭제 또는 기존 회원 탈퇴 API를 테스트 수단으로 실행하지 않는다.

Supabase 공식 문서상 ban은 기존 세션을 폐기하는 조치가 아니며, 삭제/로그아웃도 이미 발급된 JWT를 즉시 무효화하는 것으로 간주할 수 없다. 민감 API는 DB 역할 재검증 결과를 확인해야 하고 직접 Data API의 접근 토큰 유효 창도 고려해야 한다. soft delete 또한 가역적 임시 비활성화가 아니다. [사용자 관리](https://supabase.com/docs/guides/auth/managing-user-data), [세션](https://supabase.com/docs/guides/auth/sessions), [관리자 사용자 변경](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid), [삭제 API](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser).

## 테스트 프로젝트 분리와 재생성 방지 계획 — 아직 구현하지 않음

- 운영과 다른 Supabase ref·키·테스트 Auth 계정·OAuth 설정을 사용한다. 운영 Auth·관리자 계정·개인정보를 복제하지 않고 합성 데이터만 seed한다. 새로운 테스트 계정은 별도 ID를 사용한다.
- 테스트용 Vercel 환경도 별도 프로젝트 또는 승인된 테스트 브랜치 override로 분리한다. NEXT_PUBLIC_SUPABASE_URL·공개 키·서버 키·OAuth callback은 같은 테스트 프로젝트 묶음으로 검토한다. 운영 환경변수는 이 조사에서 변경하지 않는다.
- 일반 E2E setup에 앱 URL과 Supabase ref의 명시적 테스트 허용 목록 검사를 추가하는 변경을 별도 준비한다. 기본값 localhost나 프로젝트 이름 dev로 통과시키지 않는다. 운영 ref·운영 도메인/운영 DB를 쓰는 Preview이면 인증/쓰기 E2E를 실행하기 전에 실패시킨다.
- 계정 bootstrap/역할 부여는 테스트 환경 전용 서버 작업으로 제한하고 운영 키를 테스트 작업에 주입하지 않는다. 서비스 역할은 보호 guard에서도 신뢰하므로 DB 패치만으로 권한 있는 seed의 관리자 재생성까지 막는다고 가정하지 않는다.
- globalSetup의 writeEmptyState는 기존 파일이 있으면 비우지 않는다. 자격 미설정 시 이전 세션이 남는 경로를 개선하고 테스트 프로젝트 전환 시 해당 캐시를 갱신한다. 자격이 없거나 차단된 테스트를 성공으로 표기하지 않는다.
- 현재 코드에서 두 계정을 자동 생성/승격하는 명시적 실행 경로는 발견하지 못했다. globalSetup은 로그인만 하며 보안 전용 검증은 합성 계정이다. 과거 수동 AI 작업·외부 스크립트·개인 환경 전체는 미확인이다. 재생성 금지는 테스트 환경 가드·최소 권한·운영자 승인 기록을 함께 적용해야 한다.

## 복구와 미실행 범위

차단·역할 회수는 삭제보다 데이터 보존에 유리하다. 오인 대상이면 담당자가 정확한 ID와 이전 상태를 재확인하고 별도 승인으로 차단/역할을 조정한다. 테스트를 통과시키기 위해 운영 super_admin을 자동 복원하지 않는다. 삭제 후 동일 이메일로 재가입해도 원래 UUID·비밀번호·세션·참조가 복구되지 않으므로 원클릭 복구를 약속하지 않는다. 전체 DB restore도 실제 운영 계정/데이터를 되돌릴 수 있어 단순 계정 복구 대안이 아니다.

이번에는 읽기 조회와 문서 작성만 수행했다. 역할 변경·ban·세션 폐기·환경변수/캐시 변경·데이터/계정 삭제·운영 배포·Git push는 하지 않았다. 실행할 DML/계정 삭제 도구를 추가하지 않았다.
