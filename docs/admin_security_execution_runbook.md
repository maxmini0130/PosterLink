# 관리자 보호 패치와 테스트 계정 정리 최종 실행 절차

2026-10-23. 이번 작업은 읽기 전용 조사와 실행 계획 확정이다. 운영 변경 승인이 아니다. 운영자가 실제 관리자 3개(최고 관리자 1개, 관리자 2개)를 확정했고, 나머지 테스트 최고 관리자 2개만 정리 대상으로 지정했다. 실제 관리자 계정과 권한은 보존한다. 계정 이메일·UUID·개인별 로그인 시각은 이 문서와 Git에 기록하지 않는다.

## 확인된 사실과 한계

- [계정 조사](test_admin_retirement_plan.md)에서 두 대상 모두 Auth 계정과 super_admin 프로필이 확인됐다. 마지막 성공 로그인 필드는 비공개 로컬 보고서에 보존했다. 비밀번호 검증·새 로그인·토큰 사용은 하지 않았으므로 현재 로그인 성공 여부는 미검증이다.
- 관리자 감사 기록·댓글·관심 카테고리·방문 이력·알림 연결이 있다. 실제 FK에서 admin_actions.actor_user_id는 NO ACTION이므로 Auth 삭제가 차단될 수 있다. 댓글 등의 CASCADE 삭제 영향도 있다. 두 대상의 Storage 소유 객체 및 공고 작성/승인 연결은 조사 시점에 0건이었다. 삭제 직전에는 다시 조회해야 한다.
- 로컬 일반 E2E 환경과 저장된 관리자 세션이 한 대상에 의존한다. CI에 현재 로그인 의존은 발견하지 못했지만 외부·수동 자동화까지 부재를 보장하지 않는다. 기본 E2E에는 운영 프로젝트 차단 장치가 없다. Preview/localhost도 운영 DB에 연결될 수 있다.
- 운영자 제공 RLS·ACL 결과와 직접 확인한 트리거/FK 정보는 기존 조사 문서에 출처를 구분했다. 적용 직전 preflight로 전체 정책·ACL·enum·기본값·함수를 재확인한다. 오래된 조사 결과를 현재 상태로 간주해 실행하지 않는다.

## 백업과 복원 상태

2026-10-23 로그인된 운영 Supabase 대시보드를 읽기 전용으로 다시 확인했다. Scheduled backups에 일일 Physical 백업 7개와 Restore 버튼이 있다. 최신 백업은 **2026-10-22 17:45:23 UTC / 2026-10-23 02:45:23 KST**다. PITR 화면은 Enable add-on을 표시하며 현재 활성화되어 있지 않다. Restore를 누르거나 복원 시험을 하지 않았다. 따라서 백업 존재는 확인했지만 실제 복원 성공·소요시간·복원 실행 권한까지 검증한 것은 아니다. 대시보드에는 기술 문제 조사 중이라는 안내도 있어 실행 직전 서비스 상태와 해당 프로젝트 영향을 확인한다.

DB 백업에는 Storage 객체 파일이 포함되지 않는다. 복원은 특정 계정만 되돌리는 절차가 아니며 백업 이후 정상 회원·공고·댓글 변경을 잃을 수 있다. 최신 백업 이후 손실 가능 구간을 운영자가 수용하지 못하면 실행을 중단하고 별도 승인된 백업 방식을 마련한다. 실행 전에 담당자, 복원 가능한 백업 시각, 허용 중단시간과 데이터 손실 범위, ACL·정책 사전 기록 보관 위치를 확정한다.

실제 복원은 별도 승인 후 프로젝트의 Backups → Scheduled backups에서 검증한 시점을 선택해 진행한다. 재개 전에 Auth·스키마·정책·관리자 명부·웹 연결을 확인한다. 복원이 과거 취약 ACL과 테스트 최고 관리자를 되살릴 수 있으므로 유지보수 접근 제한을 유지하고 보호 패치 및 승인된 계정 차단을 재확인한 뒤 공개한다. Vercel 복구는 DB/Auth/환경변수를 복원하지 않는다.

- DB: `9510f96770c335b9b5261832f9ae6eac42063f6c`의 [보호 SQL](../supabase/migrations/20261023010000_protect_profile_role_writes.sql). Git blob UTF-8/LF SHA-256은 `597fc708cab7bd656af6a42a55ee5d0f798c5f4901470af46b8b511281196c01`이다.

## 승인 후 실행 순서와 중단 기준

1. **대상과 테스트 경로 고정:** 보호된 관리자 화면에서 유지 대상 3개와 정리 대상 2개의 정확한 Auth ID·이메일·현재 역할을 대조한다. 이름만으로 선택하지 않는다. 비공개 작업 명부에 유지 대상 ID를 명시적으로 제외하고, 대상이 정확히 2개인지 확인한다. 운영 계정을 사용하는 자동화는 중단·분리하고 해당 계정의 로컬/CI 자격·저장 세션만 폐기한다. 실제 관리자·크롤러 자격을 일괄 변경하지 않는다. 별도 테스트 프로젝트 준비 때문에 보안 패치를 무기한 지연하지 말고 의존 테스트를 중단한 상태에서 진행할 수 있다.
2. **사전 복구 준비:** 위 백업 상태와 손실 범위를 재확인하고 [preflight](../scripts/security/profile-role-preflight.sql), [ACL 기록](../scripts/security/profile-role-acl-backup.sql)을 SELECT로 실행해 보호된 위치에 보관한다. 정책·서비스 권한·enum/default/함수에 예상 밖 차이가 있으면 중단한다.
3. **웹 먼저 적용:** 별도 배포 승인 후 고정 웹 릴리스만 반영한다. 프로필 저장 요청에 role이 없고 기존 로그인·OAuth 복원·프로필 수정·실제 관리자 접근이 정상인지 승인된 계정/작업으로 확인한다. 실패하면 DB 단계로 진행하지 않는다. 정상인 role 미전송 웹 배포를 DB 적용 후 복구 지점으로 보존한다.
4. **DB 보호 적용:** 별도 DB 실행 승인 후 고정 SQL 전체를 하나의 트랜잭션으로 실행한다. 일반 사용자 role INSERT/UPDATE 권한 회수와 AFTER 보호 트리거를 함께 적용하고 기존 RLS·enum·관리자 값·정상 non-role 권한을 보존한다. 오류/timeout이면 롤백 상태를 확인하고 중단한다. 권한을 넓혀 재시도하지 않는다.
5. **보호 검증:** [postflight](../scripts/security/profile-role-postflight.sql)에서 RLS 활성, anon/authenticated role INSERT/UPDATE 4개 권한 차단, guard 정확히 1개·활성·INVOKER·고정 search_path, 서비스 및 정상 칼럼 권한 보존을 확인한다. 실제 관리자 3개 각각의 ID/역할이 사전 기록과 같아야 한다. 하나라도 불일치하면 정리 단계로 넘어가지 않는다.
6. **테스트 관리자 회수:** 별도 계정 변경 승인 후 정확한 두 대상만 super_admin → user로 변경한다. admin으로 강등하는 것은 관리자 제외가 아니다. 유지 대상 ID 제외·예상 현재 역할·대상 수 2개 조건을 작업 직전과 직후 대조한다. 다른 계정이 바뀌거나 예상 수와 다르면 즉시 중단한다. 이어서 승인된 기간으로 Auth 로그인 차단과 모든 해당 세션/refresh 자격 폐기를 수행한다. 지원되는 관리 API/대시보드와 운영 버전에 맞는 세션 폐기 방법을 실행 전에 확정해야 하며 새 로그인으로 자격을 얻지 않는다. ban만으로 기존 세션이 폐기됐다고 판단하지 않는다.
7. **사후 검증과 보존:** 실제 관리자 3개 권한 유지, 테스트 2개 관리자 권한 없음·로그인 차단 설정·세션 정리 결과를 읽기 전용으로 확인한다. 기존 토큰은 만료 전 남을 수 있어 서버 관리자 API의 DB 역할 재검증과 접근 거부도 확인한다. 로그/브라우저에 토큰·회원 목록을 출력하지 않는다. 두 Auth 계정과 연결 댓글·감사 기록은 보존한다. 즉시 Auth 삭제는 이 실행 묶음에 포함하지 않는다.

웹 적용, DB 보호 적용, 대상 두 개의 역할 회수·차단·세션 정리는 각각 명시적으로 승인받아야 한다. 이번 요청은 실행 승인이 아니다. 작업 창·담당자·허용 정상 저장 범위·차단 기간·세션 폐기 방법·복구 손실 수용이 확정되기 전에는 실행하지 않는다.

## 기능 검증 절차

- 운영자가 실제 관리자 3개로 직접 로그인해 각자 허용된 관리자 화면/API 접근과 본인 프로필 저장을 확인한다. 저장 전후 역할을 대조한다. 일반 admin에게 최고 관리자 전용 역할 변경 기능을 열지 않는다. 마지막 실제 최고 관리자 권한을 변경하는 테스트는 하지 않는다.
- 승인된 일반 회원의 정상 프로필 저장·기존 로그인/회원가입 흐름을 확인한다. 정상 저장 쓰기도 운영자가 허용한 범위에서만 한다. OAuth 실계정 검증을 하지 못하면 미검증으로 남긴다.
- 직접 SDK/REST role 변경, 타인 프로필 변경, privileged INSERT 및 간접 DEFINER 경로 차단 시험은 격리 환경에서만 수행한다. 운영에서는 카탈로그 postflight와 승인된 401/403 접근 검사로 확인한다. 정상 저장의 42501/5xx와 관리자 오류 로그를 개인정보 없이 점검한다.
- 동일 명부와 ID별 역할이 기준이다. 다른 변경이 없다면 관리자 분포는 admin 2 / super_admin 1이지만 합계만으로 성공을 판정하지 않는다.
- 기존 격리 회귀 162/162 및 보안 92개 통과 기록은 [이전 검증](profile_role_final_application.md)을 참고한다. 실제 운영 저장·로그인 성공이나 실제 PostgREST 통합 검증을 대신하지 않는다.

## 재생성 방지와 삭제의 별도 조건

현재 일반 E2E/세션 캐시 차단 장치 개선은 **계획이며 구현되지 않았다**. 운영 계정 재사용을 중단하고 별도 Supabase 프로젝트와 별도 Auth/OAuth·서비스 키·합성 seed를 사용한다. 앱 URL과 Supabase project ref 양쪽을 명시적으로 허용하고 운영 ref는 E2E/seed/관리자 부여 스크립트에서 거부한다. 자격이 없으면 과거 admin.json이 남지 않도록 별도 개선한다. 운영 service_role을 테스트에 공급하지 않는다. 트리거는 일반 회원의 상승을 막지만 정당한 service_role 자동 생성까지 막지 않으므로 외부 수동 스크립트도 담당자가 확인한다.

삭제가 필요하면 별도 후속 승인을 받는다. 직전 FK·Storage·논리 참조를 다시 조사하고 댓글/감사 기록의 보존·익명화 근거와 담당자를 확정한다. NO ACTION을 통과하려고 감사 이력을 지우거나 FK를 제거하지 않는다. 삭제된 Auth ID·비밀번호·소셜 연결을 같은 이메일 재가입으로 복원할 수 있다고 가정하지 않는다. soft delete도 임시 차단의 대체물이 아니다.

## 단계별 안전한 복구

- DB 적용 전 웹 실패: 이전 운영 배포로 복구하고 DB 작업을 중단한다. 취약점은 아직 남아 있음을 보고한다.
- DB 트랜잭션 실패: 실제 롤백과 기존 상태를 읽기 전용으로 확인한다. 부분 SQL 재실행은 하지 않는다.
- DB 보호 후 웹/프로필 실패: guard·role 제한·RLS를 유지하고 보존한 role 미전송 정상 웹으로 복구한다. 기존 운영 b3519d2는 role을 보내므로 무조건 되돌리지 않는다. 필요한 non-role 권한만 사전 ACL 근거와 별도 승인으로 복원한다. GRANT ALL, role 재부여, guard 제거는 복구 수단으로 사용하지 않는다.
- 계정 정리 중 실패: 실패 단계에서 중단하고 실제 3개 관리자 상태와 대상별 변경 이력을 확인한다. 잘못 차단된 실제 관리자 복구는 승인된 정확한 ID/사전 값으로만 한다. 테스트 계정에 super_admin을 자동 복원하거나 이미 회수한 세션을 재사용하지 않는다.
- 전체 DB 복원은 최후의 별도 승인 절차다. 데이터 손실·중단과 과거 취약 권한 재등장 위험을 수용하고 위 백업 절차를 따른다. 정상 기능 회복과 보안 보호 제거는 구분한다.
